**Damaged or missing parts.** Phase 7 asks from the product guide (`Product_Guide__c`): which part, matched to the parts list by name or sticker number; how many the set should have and how many arrived; how many of those are damaged; what is wrong; whether it was damaged in the box. When the customer is unsure what came, it goes through the guide's delivery check one group at a time. Screws and fittings are matched to the hardware list by letter (for example castor mounting screws, letter E). Every part, with the numbers received and missing or damaged, goes into one service request.

**Call handling.** These are agent settings, not prompt text. When the caller goes quiet, the agent asks whether they are there after 10 seconds of silence, again after another 10, and a third time after another 10. After 10 more seconds without an answer it says it cannot hear the caller and will end the call, then ends it. Before version 16 a single nudge after 5 seconds ended the call straight away. The caller can interrupt the agent at any time (`allow_interrupt_during_playback`). Turn-taking uses the 9-frame preset (`silence_duration_frames` 9, `analysis_frame_size` 11), so a short pause mid-sentence is not taken as the end of the caller's turn, and speech counts from -40 dBFS (was -35), so a soft voice can interrupt. The voice-activity fine-tuning (`probability_modulator_config`) is fixed by Sarvam for this workspace. The prompt adds that after an interruption the agent answers what the caller said instead of restarting, meets a cut-off sentence or a short mobile number with a brief please go on, and never ends a call because of a pause.

**Complete requests.** Before version 17 two calls left cases with no order and the customer "Unknown Customer": the caller (on a number other than the one on the order) gave a phone order's number, the request tools had only `order_id`, so the order never reached the server, and no name was passed, so the server saved a customer called Unknown Customer. Now `book_installation`, `register_service_request` and `request_human_callback` take `order_number` too, and the server finds the order from the order id, order number or invoice number the way `find_order` does. An installation, damage or replacement request is registered only for an order that is found; the case gets the order, its invoice number (or the one the caller gave) and the order's customer, and without the order the tool refuses and says what to ask, or to offer the invoice upload link. A request may use another mobile number, for example a relative's: it goes on the case, no new customer is made for it, and the full name of the person to ask for on it is required and noted on the case. No customer is ever created without a full name (any script, so हेमंत शर्मा counts); a record the agent once saved as Unknown Customer takes the full name the next time it is given, and is never greeted as Unknown. General questions and call backs can still go without an order. The prompt asks for the first and last name before any request (Phase 5 step 5), and when no order can be found and the caller declines the invoice link, offers a call back instead of registering an installation or a damage request (Phase 15). The website chat's Apex intake has none of this.

**Order confirmation.** Since draft 18 an order found by its order id, order number or invoice number is the caller's only when a number from the call is a mobile on the order's customer record (its contact or any contact of its account): the caller's number (`customer_phone`, sent by the tools as `caller_phone`), the mobile passed as `phone`, or the number the caller says the order was placed with (`order_phone`). Until then `find_order` answers `found: true, number_confirmed: false` with nothing about the order, and its message tells the agent to ask "which mobile number was this order placed with" and call it again with that number as `order_phone`. A wrong number is asked once more, then a call back is offered; an order with no mobile on record cannot be confirmed, so the agent offers the invoice upload link. The confirming number comes back as `order_phone` and is saved to the agent variable of that name, which `get_details_on_file`, `get_installation_address`, `book_installation`, `register_service_request` and `request_human_callback` send with every call, so the caller is not asked again. Those tools refuse to act on an unconfirmed order; a call back or a general question still goes, without linking the order (noted on the case). Once confirmed, the request may still name another number to be reached on, with the full name ("Complete requests"). The website chat's Apex intake has none of this.

**Tone.** The agent matches its tone to what the caller says, not to how the voice sounds: warm and positive with a pleased caller; calm, one short sorry and straight to the next step with a frustrated or angry one; simple, one step at a time with a confused one; kind and clear about what happens next with a worried one, promising nothing the guardrails forbid. It never names the caller's feelings, keeps replies short, and puts getting the request right before tone.

**Assembly help.** A customer who wants to assemble the product alone, or is stuck on a step, is walked through the complete product guide one step at a time (Phase 16). With `purpose: assembly` the tool returns the whole guide (what the product is, what comes in the set, the tools, the parts by sticker number, the hardware by letter, a parts check, every numbered step with the hardware that step uses, the tips, rules and warranty) and `step_count`, and the agent reviews all of it first. It says how many steps there are, the tools and the advice for before starting, goes through the parts check when the customer has not checked the parts, then gives each step with its number (Step 3 of 12), its parts by sticker number and its hardware by letter and name, the next step only after the customer says it is done, safety advice before electrical steps, and the care tips at the end. A missing or damaged part found on the way goes to Phase 7, and a customer who stops part way is offered an installation visit. Delivery calls offer this help when the customer prefers to assemble it alone. The agent gives only what the guide has: when a found guide has no steps, the tool's answer says so and the agent offers an installation visit, never a step or a step count of its own. No order is asked for: the product name is enough.

**Language.** Sarvam detects the caller's language from speech and switches the agent (automatic language detection is on, starting in Hindi), and the prompt has no language rules: Sarvam refuses a prompt that tells the agent to choose its reply language, so the earlier "Phase 0. Language" design (the customer picks Hindi or English at the start, detection off) cannot be used and was removed. A customer who asks in words for another language is switched by the platform. After the call, `preferred_language` is saved on the caller's contact (`Contact.Languages__c`, shown in the console) and noted on the call Task.

**Repeat requests.** Before a new installation, damage or part, or replacement or return request is registered on an order, the agent checks for an open request of the same kind on that order. `find_order` names the open kinds and the day each was registered, without request numbers. `book_installation` and `register_service_request` refuse a same-kind request unless `new_request` is true, and say what is open. The agent asks the customer whether they want an update on the open request (Phase 9, verified as usual) or a new one. A reschedule is never compared. Older cases often have no sub type, so the kinds are broad: any open installation (except a follow-up or re-installation), any damage or defect, any replacement or return. General queries and call backs are not compared. The website chat's Apex intake does not have this check.

**Installation address.** For an installation the agent asks whether to install at the address where the order was delivered or somewhere else (Phase 6 step 2, `get_installation_address`). When the customer chooses the delivery address it is not asked for again, and `book_installation` is sent `at_delivery_address`; otherwise the agent takes the new address, city and PIN code. Most older demo orders (TD-ORD-1001 to 1007) have no delivery address on the order, so the agent offers the customer's own address on file and says the order has none. The case notes which address the customer chose.

**Invoice upload link.** For any concern about an order (installation, damage, replacement, where the order is), the agent offers a WhatsApp link to upload a photo, screenshot or PDF of the invoice (Phase 15) in two cases: no order is found by the order id, order number or invoice number (asked twice) nor by the mobile number; or an order matches but has no mobile number on record, so it cannot be confirmed, or a confirmed order has no delivery address on record (`mobile_on_order`, `address_on_order`, `details_missing`; an address needs a street and a city or PIN code). For a confirmed order it first answers what the customer asked. The agent asks whether it may share the link on the customer's WhatsApp to upload the invoice slip. It confirms the WhatsApp number and the name and calls `send_invoice_upload_link`, then says the order is completed from the invoice once it is uploaded and asks the customer to call again to have the concern resolved, and closes the call. When the customer does not want the link, or it cannot be sent, the agent registers nothing for an order it could not find or confirm and offers a call back instead; for a confirmed order missing only the address it asks for the address. The customer opens the website's `/invoice` page (the same link for everyone) and uploads the invoice, nothing else; the server takes it only when Sold By is Tiffany Designs Private Limited, reads it with a Groq vision model, finds the order by the invoice number, the phone on it, the order number or the order id, and updates the order's details, customer and products from the invoice, or adds a Draft order from it when none matches; through the link sent to that phone or to the order's customer, it links the caller's open requests that have no order. See "Invoice upload links" in the main README.

**Name.** The agent introduces itself as the Tiffany Designs AI service assistant, with no personal name, and says it is an AI assistant when asked. Nothing a customer or staff member hears or sees names the voice platform: not the agent, the website (the call widget's own panel title is replaced in the page), the console, the Salesforce panel, or the text written to Salesforce records. Only technical names stay: environment variables (`SARVAM_*`), code modules, the `/api/sarvam` address and the widget library.

## Call types

`call_reason` selects the flow. Every outbound call gets its opening line from the server as `opening_line` (and `app_overrides.initial_bot_message`), and that line only confirms who answered.

| `call_reason` | Who starts it | Opening line |
| --- | --- | --- |
| `inbound` | Customer calls the Tiffany number, or the website call widget | Namaste, welcome to Tiffany Designs. How can I help you today? On a website call the widget sends it as `opening_line` with the first name when the typed mobile belongs to a customer: Namaste Satish ji, welcome to Tiffany Designs. How can I help you today? |
| `delivery_followup` | Server, 1 hour after `Delivery_Status__c` becomes Delivered | Hello, this is the Tiffany Designs AI service assistant. Am I speaking with {name}? |
| `delivery_check` | Server, `/cron/run` every 15 minutes, an hour or more after delivery (see the main README) | Hello, this is the Tiffany Designs AI service assistant, calling about your recent delivery. Am I speaking with {name}? Phase 14 then says the order, product and `delivery_date`, asks whether every part arrived, and offers an installation request only when it did |
| `callback_request` | Server, when a customer leaves a number | …calling back as requested. Am I speaking with {name}? |
| `service_update` | Server, on a case event (module 13) | Same as delivery follow-up; the update text is passed in `notice_details` |

**Caller first.** At the start of every call the on-start tool `identify_caller` sends Sarvam's caller identifier (`user_identifier`, the phone number on a phone call, with `user_identifier_type`) and the call's variables to `/api/agent/call-start`. For an inbound call the server takes the website number when one was typed, else the phone caller's number, looks it up, and answers with `customer_phone`, `customer_name` (first name), `opening_line` (the greeting by name) and `caller_details` (name, recent orders and open requests, or not on record), which are saved before the greeting is spoken. Outbound calls keep the variables the server set. The agent then never asks for the mobile number: it uses `customer_phone` in every tool, and when that number is not on record it asks only whether the order was made with another number (Phase 4 step 1, Phase 5 step 2, and the speaking rules). Until the endpoint is deployed the tool fails and the call goes on as before.

**Short greeting.** The inbound welcome was three sentences; it is now one short line. The agent's greeting (`intro_message_config.audio`, so every language) is `{{opening_line}}`, whose default is the short welcome above. Every outbound call sets its own line, and the website widget sets the welcome with the first name (`web/lib/caller.js`). Since the greeting text is the variable, it is spoken as written in every language rather than translated.

## Tools

All tools POST to the server with the `x-agent-secret` header. What the agent hears is each tool's response template ("Send fields from the API response to the agent"): the `message` field, then a line of the answer's key fields, for example `Fields: found=True, order_id=TD-ORD-1001, open_requests=['installation']`; [tools.json](tools.json) lists, per tool, every input, every response field with its meaning, the fields sent, the failure line and the variables saved. Refusals come back as HTTP 200 with the reason and what to ask next, so the agent can ask the customer for the missing detail. A non-200 response makes Sarvam play the tool's generic failure line instead, so a tool whose Salesforce call fails also answers 200: `error: "unavailable"`, the tool's usual fields empty (`created: false`, `case_number: null` and so on), and a message telling the agent to try once more and what to do after a second failure (a registering tool says nothing was saved; `place_order` falls back to a call back). The "Tool messages and problems" section of the prompt tells the agent to act on a message's instructions and never read them out.

### Phone orders

Phase 12 of the instructions: the agent finds the product with `find_products`, asks the quantity, then the name, the mobile number (it cannot see the caller ID, so it always asks for the digits), and the delivery address, city, state and PIN. It reads the order back and places it after the customer confirms. It gives the order number and the total list price and says the sales team will call to confirm. It never takes card, UPI, bank or OTP details.

The server refuses an order without a valid Indian mobile, address, city or six-digit PIN, with an unknown product code, with more than 10 products or a quantity over 10. Each refusal is spoken back so the agent can ask again. When the mobile already belongs to a customer, the order goes on that account. If the caller gave a different name, the order description says so for the sales team.

Voicemail is on: "Hello, this is Tiffany Designs customer care calling about your order. The service team will try you again later. Thank you."
