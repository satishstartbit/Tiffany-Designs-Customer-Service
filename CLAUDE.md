# Tiffany Designs Customer Service

## Sarvam voice agent

The Sarvam MCP server has access to the whole workspace, but this project owns exactly one agent:

- Agent ID: `Tiffany-Des-0db8e21d-e099` (also `SARVAM_AGENT_ID` in `.env`)
- Editor: https://indus.sarvam.ai/samvaad/build/update-agent/Tiffany-Des-0db8e21d-e099

Only read or change that agent. Never create, clone, edit, commit, or delete any other agent. Knowledge bases, secrets, campaigns, and telephony are shared across the workspace, so confirm with the user before changing them.

`.claude/hooks/sarvam-agent-guard.js` enforces this: it blocks Sarvam MCP writes that target a different agent ID and asks before workspace-level changes.

`sarvam/agent-prompt.md` is the source of the agent's instructions and `sarvam/tools.json` lists its tool IDs and endpoints; keep both in step with what is pushed to Sarvam. The workspace number `+917965851546` belongs to another agent's deployment, so never deploy or campaign Tiffany on it; `SARVAM_AGENT_PHONE` uses it only as a caller ID for test calls until Tiffany has its own number.

## Salesforce

`salesforce/force-app` holds what this project deploys to the org (the website "call me" panel, its Apex, the `Tiffany_Voice_API` credential and permission set); deploy with `npm run deploy:salesforce`, which validates and runs the Apex tests. The `Tiffany_Agent_API` credential, `AgentChatController` and `tiffanyChat` belong to the site's Agentforce chat: never change them.

The Node server owns its intake logic (order verification, case creation, business hours in `src/crm/`) and talks to Salesforce only through the standard REST data API; it must not call Apex. The site chat still uses the org's Apex intake (`ServiceIntakeService`), so when the verification or case rules change in one, mirror them in the other. Known difference: the voice agent also accepts the full name instead of the mobile (with an order, invoice or request number, or with a PIN code); the Apex intake still requires the invoice number or mobile. The voice agent keeps one open installation, damage or replacement request of each kind per order: a request of the same kind as an open one is added to that one as an update (a reschedule moves it), and a new request is registered only when none of that kind is open, also when an earlier one is closed (`createServiceCase` in `src/crm/crm.js`); the Apex intake has no such check. When no order is found, or the order has no mobile number or delivery address, the voice agent offers a WhatsApp link to upload the invoice, and once the customer says it is uploaded (on the same call, or after calling again) looks up the order the upload found or added and carries on (`src/invoiceLinks.js`, `src/crm/invoiceUploads.js`, `check_invoice_upload`); the Apex intake has no such step. The voice agent accepts an installation slot only Monday to Saturday, 10 am to 6 pm IST, and still ahead (`src/installationSlots.js`); the Apex intake has no such check. The voice agent gives an order's details, and registers anything for the order, only once a number from the call (the caller's, or the number the caller says the order was placed with, `order_phone`) is a mobile on the order's customer record (`confirmOrderNumber` in `src/crm/crm.js`); the Apex intake has no such check. The voice agent registers installation, damage and replacement requests only for an order it finds (order id, order number or invoice number), puts the order's customer on the case, needs the full name of the person to contact when the mobile is not on the customer's record, and never saves a customer without a full name (`createServiceCase` in `src/crm/crm.js`); the Apex intake has no such rule. The voice agent finds a caller's orders and requests on every customer record their number is on, lists them when there are several, and finds orders by full name with PIN code (named only until a number confirms one); the Apex intake has no such search. The voice agent saves a request, an order or customer details on a mobile number only once the caller has confirmed its last four digits (`contact_number_ending`, `numberToConfirm` in `src/rules.js`), and takes "use my current number" as the number of the call, filled in by the server (`use_calling_number`); the Apex intake has no such check. Both are left unchanged until the user decides the website chat should follow. The Experience site is public (guest user), so anything exposed to it needs server-side limits.

Write agent instructions in the voice Sarvam's playbook requires (third person, no quotes, `call tool:name`), and never let the model do date arithmetic: dates go through `resolve_date`. Never let the model count digits either: it passes a PIN code or a mobile number as heard ("30 20 20") to `check_number` and reads back what that answers, and the server reads and counts it in every tool and says back what does not fit (`digitsSaid` in `src/rules.js`, `saidNumberProblem` in `src/routes/agentTools.js`). The prompt and tool definitions sit close to the model's token budget (with `token_based_truncation`, overflow drops the customer's words and the agent replies with its greeting), so keep tool descriptions short, put instructions in the prompt once, and test a long tool answer in a chat before committing. Long calls drop earlier tool answers from what the model sees, so part and hardware details are looked up again with `get_product_guide` `item` (one sticker number, letter, step, box or name, `guideItem` in `src/crm/productGuides.js`) rather than given from memory, and a guide keeps each part's sticker number (the console refuses a parts list without them while the parts carry stickers).

## Website (web/)

`web/` is the Next.js site deployed on Vercel (Root Directory `web`): the staff service console (behind a sign-in) and the public customer care page `/support` with the browser call widget (the console itself has no widget) and, with `SUPPORT_CHAT=on`, a text chat (`web/lib/chat.js`, `components/ChatAgent.js`): the widget's panel then offers Call and Chat under the mobile number. Sarvam has no text chat for the voice agent, so the Node server runs the chat (`src/chat/`, `/api/chat`): a Groq text model (free plan, 8,000 tokens a minute per model, so keep its prompt and tool definitions short) with `sarvam/chat-prompt.md` and the voice agent's own tools through `/api/agent`; keep `chat-prompt.md` in step with the rules in `agent-prompt.md`. The site reaches it through its own `/api/chat` (`web/lib/chatSession.js`), within the call limits. The public page may read only the service hours (`loadSupportHours`) and, through the web-call session route when it hands out a call link (so within the call limits), the first name of the customer whose mobile number the caller typed (`lookupCaller`, `/api/admin/caller`), which goes to the agent as `customer_name`; the chat, started within the same limits, works only through the voice agent's tools and their checks; everything else needs the staff session. The one other public page is `/invoice`, the fixed address the WhatsApp link points to: it asks for nothing but the invoice file and sends only that, through its own route (`web/lib/invoiceUpload.js`, no key) to the Node server's public `/api/invoice-uploads`, which rate-limits uploads, takes only invoices sold by Tiffany Designs Private Limited, and finds the customer and the order from the invoice itself, or adds an order from it when none matches: created Draft for its products, then activated and marked Delivered on the day of the upload (`deliverAdded` in `src/crm/invoiceUploads.js`), and skipped by the delivery check calls. It adds an order only when the invoice number is printed, every product is an active catalog product, and none of the invoice number, order number and order id is already on several orders (one order holding it is the match); otherwise it refuses the upload, or hands it to the service team. Its answers never include Salesforce data. The console reaches Salesforce only through the Node server's `/api/admin` (`src/routes/admin.js`, `src/crm/console.js`): read-only views, plus order edits limited to the fields in `ORDER_EDITS`, customer edits limited to `CUSTOMER_EDITS` (`src/crm/customers.js`; on the customer's page and with the order on the order edit page) and product guide edits limited to `GUIDE_FIELDS` (`src/crm/productGuides.js`), each checked against the org's describe and noted as a completed task naming the editor. The voice agent finds callers and confirms orders by a customer's mobile and phone numbers, so customer edits save mobiles in +91 form and refuse a number another customer already has. It calls it with `NODE_API_KEY`, from server code (`web/lib/api.js`, marked server-only); browser components never import it. It has its own copy of the web-call session route (`web/lib/webSession.js`, `web/lib/limits.js`); keep it in step with `src/routes/webCalls.js` and `src/rateLimit.js`. Keys and passwords live only in server environments (`web/.env.local`, Vercel variables), never in browser code or `NEXT_PUBLIC_` variables. The look follows the ROCCO storefront (warm off-white, black uppercase buttons, maroon accents, Red Hat Display).
